## In plain words

CoResearcher checks scientific claims; it does not invent them. You give it a hypothesis (in prose, or written as
explicit variables and constraints), and it tells you, with reasons that anyone can re-run:

- whether the hypothesis says anything at all, or could never be proved wrong;
- whether its own assumptions contradict each other;
- which situations would prove it wrong;
- how it relates to rival hypotheses, and what follows from it;
- whether the results it borrows from other papers are used under the conditions those papers proved them;
- how far each claim has really been checked, from "only written down" to "checked by a proof assistant".

When CoResearcher cannot decide something, it says so ("open", "blocked", "undecided") instead of guessing. Around
these checks it keeps tamper-evident records: what was fixed in advance, which results depend on which premises, and
which stage of a research project has passed its gate.

The repository also holds many engines from earlier phases of the project (2025 to mid-2026). Some still compute
something real; many return scripted results, match keywords, or apply a fixed threshold to numbers the caller
supplies. They are listed here with those caveats, so nobody mistakes them for working science. The parts that carry
the product today are the formal core, the verification chain, the statement and manuscript audits, the registry
and ledgers, the biomedical checks, the regression benchmarks and the research lifecycle.

The map covers **59 capabilities** in 11 groups: 141 REST endpoints, 30 CLI commands and 157 Python modules, plus every script, example, benchmark file and integration in the repository (except `archive/`).

## How to read an entry

Each capability lists:

- **What it does**, in plain words, and a **status** line where the capability is legacy, scripted or withdrawn.
- **Verification chain (ADR-085)**: the step it performs in the composed chain (`POST /api/chain/run`,
  `coresearcher chain run`), if any. The chain runs freeze, formalize, fidelity, vacuity, obligations, seams,
  discharge and trust ladder, in that order ([VERIFICATION_METHODOLOGY.md](VERIFICATION_METHODOLOGY.md), section 3).
- **Caveats**: scripted demos, keyword heuristics, thresholds on caller-supplied numbers, withdrawn or unvalidated
  benchmarks. A capability without caveats can still be wrong; the [claims register](../reference/CLAIMS_REGISTER.md)
  says what has been measured.
- **Modules**, with the maturity level from the [module register](../reference/MODULE_MATURITY.md) (integrated,
  tested, exercised, prototype; modules outside `python/discovery/` are outside that register) and the number of
  endpoints whose code refers to the module directly. The register marks a module as API-reachable only when its name
  appears under `api/`; routers that import classes through `python.discovery` re-exports are missed, so the endpoint
  count here is the better measure of reach.
- **Endpoints** and **CLI** commands, read from the code. The [API reference](../reference/API.md) has the schemas.
- **ADRs** cited by the capability's own source files, and **tests** that mention its modules, scripts or paths.

## Formal core

Hypotheses as formal objects: variables, constraints and claims over a declared state space, decided exactly by enumeration or by the z3 solver, with explicit non-verdicts when nothing can be decided. Everything else that checks a hypothesis builds on this group.

<a id="formal-hypotheses"></a>

### Formal hypotheses and exact evaluation

Represents a hypothesis as variables, constraints and claims over a declared state space, and decides questions about it exactly: whether it forbids anything (falsifiability), whether its assumptions conflict, which states refute it, how it relates to a rival (equivalent, stronger, weaker, compatible, incompatible) and whether a consequence follows. Finite spaces are enumerated; continuous and unbounded integer variables go to z3 (ADR-060, ADR-090). Every result carries a status from a shared vocabulary (decided, open, blocked, undecided, invalid input), named and versioned thresholds, and a provenance block saying which engine and solver produced it (ADR-068). Hypotheses can be case-scoped (ADR-089).

**Verification chain (ADR-085):** Step 7, discharge (M8): obligations that are formal consequences are decided here by z3 or enumeration, never turning an unknown into a verdict. Step 4, vacuity (M4): the evaluator's declared non-witness probe (ADR-080).

**Caveats:**

- Verdicts are exact only for the variables and constraints as declared; whether the declaration matches the scientist's intent is the job of the fidelity and formalization checks.
- z3 runs under a timeout (formal_thresholds); a timeout is reported as UNDECIDED, never as a verdict.

<a id="formalizer-gate"></a>

### Formalizer and self-consistency gate

Turns a hypothesis written in prose into the formal object, using a local language model as a translator only. The default path is formalizer v2 (ADR-093): translation rules and worked examples, JSON mode, a surface-syntax repair that never changes meaning, and one self-repair round fed with the validator's error. The gate draws several independent formalizations and accepts one only when a strict majority are exactly equivalent (decided by z3 or enumeration); otherwise it returns FORMALIZATION_AMBIGUOUS or FORMALIZATION_FAILED. Accepted results are drafts pending the scientist's review.

**Verification chain (ADR-085):** Step 2, formalize (M2): independent readings that must agree (ADR-064).

**Caveats:**

- Needs a configured local model (OpenAI-compatible endpoint); without one the endpoint reports BLOCKED.
- Fidelity of prose-to-formal translation is measured, not established: under a frozen protocol v2 reached 67-100% equivalence to gold on a 12-item held-out set across four local models (v1: 17-92%), with named remaining failure kinds (FORMALIZER_V2_RESULTS.md). The gate keeps unstable formalizations out but lets consistent, systematic errors through (claims register row 29).

<a id="kernel-records"></a>

### Recorded Lean kernel checks

A GitHub Actions workflow (Lean kernel checks) runs the Lean kernel on a Linux runner, on our Lean files and on openai/math Comparator challenges, and writes a kernel record next to the full run log: what was checked (file hash, toolchain, Mathlib commit), the axioms each theorem uses, the wall time and the result. The result is recomputed from the log, never trusted from the record. A hash-verified PASS record is the only way a claim reaches KERNEL_CHECKED; the climb for a registry entry is `POST /api/registry/entries/{entry_id}/kernel-check` (listed under the registry).

**Verification chain (ADR-085):** Feeds step 8, trust ladder (M7): the top rung needs a verified kernel record (ADR-092).

**Caveats:**

- BLOCKED (the kernel did not run or did not finish) is a non-verdict and never climbs.
- Records exist only for the targets the workflow has run (records/kernel/); everything else stays below KERNEL_CHECKED.

## Verification chain

The eight methods of VERIFICATION_METHODOLOGY.md composed into one flow (ADR-085): fix the acceptance criteria first, formalize, check fidelity and vacuity, decompose into obligations, check the seams, discharge, and grade every claim on the trust ladder.

<a id="verification-chain"></a>

### Composed verification chain

Runs a submitted hypothesis (formal, prose, or a biomedical mechanism) through the eight steps of the methodology in one call and reports each step's state: DONE, OPEN, NOT_APPLICABLE, NOT_RUN or a non-verdict. A non-verdict stops the chain, and later steps are NOT_RUN. The final report grades every claim on the trust ladder.

**Verification chain (ADR-085):** The chain itself (ADR-085): freeze, formalize, fidelity, vacuity, obligations, seams, discharge, trust ladder.

**Caveats:**

- Fidelity stays OPEN unless the scientist supplies a fidelity specification, and vacuity stays OPEN unless non-witnesses are declared: there is no independent formal reading of the prose to compare against.
- On the openai/math time-travel corpus the full chain decided 1 of 17 corrected defects, the same unresolved citation the first run found (OPENAI_MATH_CHAIN_RESULTS.md).

<a id="freeze-service"></a>

### Freeze service (acceptance criteria fixed in advance)

Records, before anything is evaluated, what would count as support or refutation: the discriminating states of a hypothesis against its rivals, or the SHA-256 of a protocol or checklist. A later verification says whether the freeze still holds for what is about to be evaluated; a mismatch blocks the evaluation. Freezes go to a hash-chained log and can be anchored in a lifecycle project.

**Verification chain (ADR-085):** Step 1, freeze (M3). A freeze made in the same run is reported with the weaker relay CRITERIA_FROZEN_IN_SAME_RUN.

## Registry and ledgers

<a id="cited-registry"></a>

### Registry of cited results and premises

Keeps versioned entries for results a hypothesis imports from other papers, with their typed hypotheses and conventions (assay, units, population, sign conventions). **Caveats:**

- Entries are written by people or agents from the cited source; the registry checks uses against what an entry says, not whether the entry is faithful to the source.

## How this map is kept current

`scripts/generate_capability_map.py` rebuilds this page and
[`ecosystem/registry/capabilities.json`](../../ecosystem/registry/capabilities.json) from the code and from
[`capability_annotations.toml`](capability_annotations.toml). CI runs it with `--check` in the repo-consistency job.
The check fails when:

- an endpoint, CLI command, module, script, example, benchmark file or integration entry belongs to no capability,
  or to more than one;
- an annotation pattern matches nothing (the code it described is gone);
- the AST scan of `api/` and the committed OpenAPI contract disagree;
- this page or the registry file differs from what the generator writes.

`tests/test_capability_map.py` checks that the endpoints of `GET /api/capabilities` (the runtime catalogue, ADR-067)
are exactly the endpoints of the registry, and that both report the same maturity for each module.

To add a capability: write the code, add an entry to the annotations file (id, title, group, what, the patterns that
claim its files, endpoints and commands, and its caveats), run `python scripts/generate_capability_map.py`, and
commit the three files together.
